# Планирование, анализ, идентификация проблем и поиск решений

## Анализ архитектуры и идентификация проблем

### Существующие и потенциальные проблемные места

1. **Неоптимизированный дашборд заказов**: Дашборд (главная страница) MES долго грузится. Предыдущие попытки это поправить не помогли, что указывает на фундаментальные проблемы с проектированием БД и доступа к БД.

2. **Немасштабируемость расчета стоимости моделей**: Длительный расчёт стоимости моделей выполняется в MES синхронно в рамках запроса по API от партнеров или онлайн-магазина. Это блокирует ресурсы, вызывает таймауты и является точкой отказа.

3. **Смешение ответственности сервисов**: API для партнёров использует MES для расчёта стоимости моделей, и только потом заказ создаётся в CRM через сообщение от MES - это создаёт циклическую и неочевидную зависимость и нарушает принципы ответственности сервисов.

4. **Ненадежность и немасштабируемость баз данных**: Базы данных развёрнуты на одном инстансе - это значит, что при падении инстанса БД приложения полностью перестают работать. Также использование одного инстанса для записи и чтения не позволяет точечно масштабировать нагрузку на запись и чтение данных.

5. **Ненадежность и немасштабируемость приложений**: Приложения развёрнуты в единственном экземпляре - это значит, что при падении инстанса приложения система становится полностью недоступна. Также все приложения работают напрямую с базами данных, что повышает нагрузку на них, а также не позволяет масштабировать чтение.

6. **Риски безопасности**: Партнеры обращаются напрямую к MES API. MES является core-domain системой, что означает, что она должна быть изолирована от внешнего доступа с помощью прокси (api gateway, load balancer).

7. **Отсутствие наблюдаемости**: Команда узнаёт о проблемах из жалоб пользователей, а не из метрик, что говорит о том, что не внедрены системы мониторинга, централизованного логирования и распределенной трассировки.

8. **Разрозненный технологический стек**: Два бэкенда на Java и один на C# увеличивают нагрузку на команду по поддержке и развитию, требуют разных экспертиз и усложняют кросс-функциональную работу, в будущем этом может стать ограничивающим фактором роста либо увеличения стоимости сопровождения системы.

9. **Отсутствие автоматизированных тестов**: E2E-сценарии прогоняются вручную, что говорит о том, что в компании отсутствует автоматизации тестирования. Это выливается во всё более продолжительное время тестирования и релизов.

10. **Неэффективный CI/CD**: Автоматический деплой в dev-окружение после мёрджа пул-реквеста говорит о неэффективном процессе CI: ветка не тестируется QA-инженером до мержа, что и вызывает блокировку релиза до исправления багов. Также ручное тестирование на релизных окружениях и ручной деплой — это медленно и чревато человеческими ошибками.

11. **Несбалансированный состав команды**: В команде 5 разработчиков (2 фронтендера и 3 бэкендера) и всего один QA-инженер. С учетом того факта, что тестирование осуществляется вручную, а деплой не автоматизирован, ресурс тестирования критически мал.

## Инициативы для устранения проблем с приоритетами

Приоритеты расставлены на основе критичности для бизнеса и логики улучшения системы: сначала сделать её наблюдаемой, затем устранить критические проблемы производительности и надежности, далее улучшить тестируемость для ускорения разработки.

1. **Внедрение мониторинга и observability** (высокий приоритет): Развернуть стек для сбора метрик и визуализации дашбордов. Внедрить в приложения сбор метрик (время ответа MES, количество сообщений в очередях, ошибки и тп). Настроить централизованное логирование. Настроить распределенную трассировку между сервисами. Позволит "увидеть" проблемы, обосновать изменения, быстро реагировать на инциденты.

2. **Увеличение отказоустойчивости баз данных** (высокий приоритет): Перевести базы данных на кластерные решения с одним мастером (на запись) и несколькими репликами (на чтение). Это устранит SPOF и позволит распределять нагрузку на чтение.

3. **Увеличение отказоустойчивости приложений** (высокий приоритет): Отрефакторить приложения для возможности запуска множественных экземпляров. Развернуть новые контейнеры и добавить в пайплайн деплой копий приложений.

4. **Перевод расчёта стоимости моделей в асинхронный режим** (высокий приоритет): Онлайн-магазин и партнёрский API должны инициировать запрос на расчёт и немедленно получать в ответ request_id, MES считает стоимость модели в фоновом режиме и отправляет событие PRICE_CALCULATED с request_id в очередь, сервисы-инициаторы подписываются на это событие и уведомляют пользователя.

5. **Оптимизация БД MES** (высокий приоритет): Провести аудит и профилирование медленных запросов на дашборде. Добавить индексы, переписать запросы, денормализировать данные для часто запрашиваемых представлений или добавить материализованные представления.

6. **Внедрение кэширования в API MES** (средний приоритет): Внедрить кеширование для данных дашборда. Внедрить кеширование для результатов расчёта стоимости моделей.

7. **Разработка API Gateway** (средний приоритет): Разработать и ввести в строй партнерский API (api gateway), чтоб партнеры не ходили напрямую в API MES.

8. **Устранение циклической зависимости MES и CRM** (средний приоритет): Заказ должен создаваться в CRM через партнерский API, а затем CRM отправляет асинхронное сообщение SUBMITTED в MES для расчёта стоимости.

9. **Найм QA-инженеров** (средний приоритет): Найм QA-инженеров для устранения бутылочного горлышка процессов тестирования и деплоя.

10. **Написание тестов** (средний приоритет): Проанализировать ключевые пользовательские пути, разработать end-to-end тесты, внедрить тесты в пайплайн.

11. **Автоматизация CI/CD пайплайна** (низкий приоритет): Автоматизировать деплой в release и prod окружения с ручным подтверждением.

12. **Декомпозиция сервисов на микросервисы** (низкий приоритет): Выделить отдельный сервис для работы с заказом (OrderService) с переносом логики в него из Shop API и CRM API.

13. **Унификация технологического стека** (низкий приоритет): Выбрать стратегию развития технологического стека компании.


## Целевая архитектура через полгода

Через полгода архитектура должна быть наблюдаемой, отказоустойчивой, более масштабируемой, с асинхронными коммуникациями между сервисами, с более четко выделенными ответственностями между сервисами, и с более эффективным CI/CD.

## Три пункта для выполнения в ближайшие полгода

1. **Улучшение наблюдаемости**: Разворачивание observability-стека (ELK, APM, Prometheus, Grafana), определение ключевых бизнес-метрик, внедрение логгирования, трассировки и сбора метрик в приложения, добавление дашбордов и алертинга. Эта инициатива позволит сделать процессы в системе более прозрачными, даст обоснование дальнейшим изменениям, позволит более быстро реагировать на проблемы и инциденты, даст разработчикам больше информации для принятия решений.

2. **Улучшение надежности и производительности**: Перевод баз данных на кластерную архитектуру с репликацией, внедрение Redis для распределенного кэширования, асинхронный расчет стоимости моделей. Эта инициатива снимет нагрузку с API MES и устранит таймауты для партнёров и пользователей онлайн-магазина, что улучшит восприятие сервиса снаружи. Также оптимизация дашбордов улучшит главную болевую точку внутренних пользователей (операторов), за счет чего повысится их эффективность и снизится уровень стресса. Предотвратятся катастрофические простои системы, будет заложена основа для будущего роста.

3. **Улучшение тестируемости**: Написание автоматизированных E2E тестов, найм QA-инженера. Эта инициатива устранит "бутылочное горлышко" процесса разработки, что повысит качество тестирования, которое положительно отразится на восприятии сервиса, а также ускорит доставку новых функций в продакшн, что позволит разработке быстрее реагировать на потребности бизнеса.

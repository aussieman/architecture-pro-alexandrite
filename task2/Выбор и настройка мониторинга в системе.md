# Выбор и настройка мониторинга в системе

## Мотивация

Внедрение мониторинга критически важно для компании "Александрит", поскольку текущая система страдает от проблем производительности, надежности и масштабируемости. Без мониторинга команда узнает о проблемах только из жалоб пользователей, что приводит к потере заказов, контрактов и недовольству клиентов. Мониторинг позволит:

- **Раннее обнаружение проблем**: Вместо реактивного подхода (жалобы) перейти к проактивному - отслеживать метрики в реальном времени и реагировать до эскалации.
- **Обоснование решений**: Метрики дадут количественные данные для приоритезации инициатив, таких как оптимизация MES или масштабирование инфраструктуры.
- **Улучшение надежности**: Отслеживание ошибок, задержек и насыщения предотвратит простои и улучшит пользовательский опыт.
- **Экономическая выгода**: Снижение времени на диагностику проблем ускорит разработку, уменьшит потери от просроченных заказов и повысит удовлетворенность клиентов и партнеров.
- **Масштабируемость**: Метрики помогут планировать рост, например, добавление инстансов при росте нагрузки.

Бизнесу это даст уверенность в стабильности системы, возможность быстрее реагировать на изменения рынка и обосновать инвестиции в инфраструктуру.

## Выбор подхода к мониторингу

Для разных частей системы выберем подходящие подходы:

- **Сервисы (онлайн-магазин, CRM, MES, API Gateway)**: "Четыре золотых сигнала" (Latency, Traffic, Errors, Saturation). Этот подход фокусируется на пользовательском опыте и системных ограничениях, идеален для приложений.
- **Инфраструктура (БД, RabbitMQ, EC2 инстансы)**: USE (Utilization, Saturation, Errors). Подходит для ресурсов, где важно отслеживать использование и насыщение.
- **Интеграции (RabbitMQ очереди)**: RED (Rate, Errors, Duration). Для очередей и асинхронных коммуникаций.

## Метрики для отслеживания

### Метрики для сервисов (Four Golden Signals)

1. **Latency (Задержка)**: Время ответа на запросы (например, расчет стоимости в MES, загрузка дашборда).
   - Зачем: Показывает производительность с точки зрения пользователя. Высокая задержка приводит к таймаутам и жалобам.
   - Ярлыки: service (MES, CRM), endpoint (calculate_price, dashboard), user_type (customer, operator, api_user).

2. **Traffic (Трафик)**: Количество запросов в секунду (RPS).
   - Зачем: Отслеживает нагрузку, помогает планировать масштабирование.
   - Ярлыки: service, method (GET, POST), source (web, api).

3. **Errors (Ошибки)**: Процент ошибочных запросов.
   - Зачем: Выявляет проблемы в коде или интеграциях, предотвращает потерю заказов.
   - Ярлыки: service, error_type (4xx, 5xx), cause (timeout, db_error).

4. **Saturation (Насыщение)**: Уровень использования ресурсов (CPU, память для приложений).
   - Зачем: Предупреждает о bottleneck'ах перед простоями.
   - Ярлыки: service, resource (cpu, memory).

### Метрики для инфраструктуры (USE)

5. **Utilization (Использование)**: Процент использования CPU, памяти, диска для EC2 и БД.
   - Зачем: Определяет, насколько эффективно используются ресурсы.
   - Ярлыки: instance_id, resource_type.

6. **Saturation (Насыщение)**: Очереди запросов, уровень загрузки диска.
   - Зачем: Показывает, когда система на пределе и нужна оптимизация.
   - Ярлыки: component (db, mq).

7. **Errors (Ошибки)**: Количество ошибок в БД (deadlocks, timeouts) или MQ (lost messages).
   - Зачем: Диагностирует проблемы надежности.
   - Ярлыки: component, error_code.

### Метрики для интеграций (RED)

8. **Rate (Скорость)**: Количество сообщений в очередях RabbitMQ.
   - Зачем: Отслеживает поток заказов между сервисами.
   - Ярлыки: queue_name (orders, prices), direction (in, out).

9. **Errors (Ошибки)**: Потерянные или не обработанные сообщения.
   - Зачем: Предотвращает потерю заказов.
   - Ярлыки: queue_name, error_reason (timeout, parse_error).

10. **Duration (Длительность)**: Время обработки сообщений.
    - Зачем: Выявляет задержки в интеграциях.
    - Ярлыки: queue_name, consumer (CRM, MES).

### Дополнительные метрики

11. **Бизнес-метрики**: Количество заказов в день, среднее время обработки, процент просроченных заказов.
    - Зачем: Связывает технические метрики с бизнес-результатами.
    - Ярлыки: order_type (b2c, api), status (initiated, completed).

12. **Доступность сервисов**: Uptime каждого сервиса.
    - Зачем: Мониторит SLA и надежность.
    - Ярлыки: service.

## План действий

1. **Выбор и развертывание стека мониторинга**: Настроить Prometheus для сбора метрик, Grafana для визуализации, ELK (Elasticsearch, Logstash, Kibana) для логирования, Jaeger для трассировки. Развернуть в Yandex Cloud.

2. **Инструментация приложений**: Добавить метрики в код (используя Micrometer для Java/C#), настроить сбор latency, errors, traffic.

3. **Настройка инфраструктурного мониторинга**: Интегрировать Yandex Cloud Monitoring для EC2, БД и MQ. Настроить алерты на saturation и errors.

4. **Определение дашбордов и алертов**: Создать дашборды для Four Golden Signals, USE, RED. Настроить алерты (Slack/email) на превышение порогов (например, latency > 5s).

5. **Тестирование и обучение**: Протестировать сбор метрик на dev-окружении, обучить команду использованию инструментов.

6. **Интеграция в CI/CD**: Автоматизировать развертывание мониторинга в пайплайне.

7. **Анализ и итерации**: Через месяц проанализировать метрики, скорректировать пороги и добавить новые метрики при необходимости.
